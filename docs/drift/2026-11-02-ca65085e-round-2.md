# Round two against `ca65085e`: queued fixes + the Azure Rust SDK review (same upstream baseline)

A follow-up to [`2026-11-02-ca65085e`](2026-11-02-ca65085e.md) against the
same baseline. It works through items that pass triaged as applicable but
left queued, and adds a standalone review of what Microsoft actually ships
for Rust: [`docs/azure-rust-sdk.md`](../azure-rust-sdk.md).

Three changes landed, each with regression tests. Two of them are live
defects in this port that upstream's own commits only partly describe,
because this port had drifted further than upstream had: one loses the
provider's error detail outright, and one is **intermittently** wrong rather
than consistently wrong, which is worse to diagnose.

Verified before commit: full workspace build, `cargo test --workspace
--all-features`, `cargo clippy --workspace --all-features --all-targets
-- -D warnings` and `cargo fmt --all --check`, all green.

## Ported (3 changes)

### `list()` could report a superseded checkpoint as the newest one (#9261)

Upstream's `get_latest` picked `max()` by timestamp alone, so two
checkpoints sharing a timestamp made the result depend on save order and a
resume could restore a superseded checkpoint. Its fix walks
`previous_checkpoint_id` to skip any checkpoint another one names as its
parent.

**This port has no `get_latest` and no `previous_checkpoint_id`**, so the
commit looked inapplicable at first. It is not: the same defect is here in a
different place. `CheckpointStorage::list` sorted by `timestamp_millis`
alone, which is not a total order, and checkpoints are written one per
superstep boundary so two of them routinely share a millisecond. The tie
then fell to however the backend enumerated — and for
`InMemoryCheckpointStorage` that is `HashMap` iteration order, which Rust
randomises per process. A caller reading the end of the list as "the newest
checkpoint" got an arbitrary one of the tied pair, *differently on different
runs of the same program*.

Measured, not assumed: with the fix reverted, the new in-memory regression
test fails **9 times in 20 runs**. That is the signature of this class of
bug — it would have shown up as a flaky resume, not a reproducible one.

`list` now sorts with a new public `compare_checkpoints`, a total order over
`(timestamp_millis, iteration_count, checkpoint_id)`:

- `iteration_count` is the superstep counter, so between two checkpoints of
  one run sharing a timestamp, the higher is the later. **That is the same
  supersession upstream recovers by walking `previous_checkpoint_id`** — this
  port does not need a lineage field because the superstep counter already
  encodes it.
- `checkpoint_id` is the final key so checkpoints from *different* runs that
  collide on both timestamp and superstep still come back in a stable order
  rather than an arbitrary one.

The order is now part of the trait's documented contract, and
`compare_checkpoints` is exported so an out-of-tree store can honour it.
Applied to all three stores: `InMemoryCheckpointStorage`,
`FileCheckpointStorage` (where the tie fell to directory order) and
`agent-framework-cosmos`'s `CosmosCheckpointStorage` (where it fell to
Cosmos's row order), matching upstream applying its fix to core, Cosmos and
Foundry.

`crates/agent-framework-core/src/workflow/{checkpoint,mod}.rs`,
`crates/agent-framework-cosmos/src/checkpoint_storage.rs`; tests
`checkpoints_sharing_a_timestamp_order_by_superstep`,
`a_newer_timestamp_wins_over_a_higher_superstep`,
`a_full_tie_is_broken_deterministically_by_id`,
`in_memory_list_puts_the_newest_checkpoint_last_despite_a_timestamp_tie` and
`file_list_puts_the_newest_checkpoint_last_despite_a_timestamp_tie`. The two
storage-level tests fail pre-fix (the in-memory one intermittently, as
above); the three comparator tests are new-API tests and cannot run pre-fix.

### Streamed Responses errors dropped the provider's code and parameter (#9616)

Upstream kept `code`, `message` and `param` from a flat Responses `error`
event as structured attributes on its own exception type instead of
flattening them into a string.

Two defects here, and the second is the serious one:

- **`code` and `param` never reached the caller.** The handler read
  `message` and used `code` only to classify a content filter, so a streamed
  `400` surfaced as bare text like `"Invalid value"` with nothing naming the
  offending field. This port was *worse off than upstream pre-fix*, which at
  least formatted both into the message.
- **A flat `error` event lost its message entirely.** The handler looked for
  the error under `response.error` or a top-level `error` key. A flat `error`
  event (upstream's `ResponseErrorEvent`) carries `code` / `message` /
  `param` *on the event itself*, nested under nothing — so none of the three
  was found and every such event collapsed to the generic
  `"response failed"`, discarding whatever the provider actually said.

Both are fixed: the event itself is the last fallback for the error object,
and `code` and `param` are formatted into the message the way upstream
formats its own (`"{code}: {message} (parameter: {param})"`), each clause
omitted when absent so the common shape grows no `None:` noise.
`Error::service` carries a string rather than fields, which is why they go
in the message here; the content-filter classification is unchanged and
still keyed on the raw `code`.

`response.failed` events are unaffected by the fallback — they carry no
top-level `message`, so they still reach the `"response failed"` default.

**This reaches Azure for free.** `agent-framework-azure`'s
`get_streaming_response` calls
`agent_framework_openai::responses::parse_responses_sse_stream`, so Azure
OpenAI and Foundry (which wraps it) get the same fix from one change.

`crates/agent-framework-openai/src/responses.rs`; tests
`a_streamed_error_keeps_the_provider_code_and_param`,
`a_streamed_error_without_a_code_or_param_is_just_its_message` and
`a_content_filter_block_keeps_its_classification_and_its_code`. All three
fail pre-fix.

### Exported telemetry was not identifiable as Agent Framework's (#9589)

Upstream added `microsoft.agent-framework="True"` to the OTel resource
shared by its logs, traces and metrics. Azure's agent telemetry views —
Foundry's, and the Application Insights experiences built on them — key off
that attribute to tell Agent Framework telemetry apart from an
application's own, so a pipeline without it exports telemetry those views do
not recognise.

`otel-export`'s pipeline builds one `Resource` and hands it to both the
tracer and the meter provider, which is already upstream's shape, so the
attribute was added there and covers both signals. The resource construction
moved into a small `build_resource` so the attribute is testable without
standing up an exporter.

The value is the string `"True"`, not a boolean, matching upstream's
`resource_attributes` default exactly — the two are distinct values on the
wire and a consumer matching the string would not match a bool.

Also corrected two now-wrong doc comments on `ObservabilityConfig` that said
"this crate does **not** build an OTel `Resource`, exporter, or
`MeterProvider`". That predates the `otel-export` feature, which builds all
three. It is worth more than a wording nit: a reader who believed it would
wire their own `Resource` and silently omit the very attribute this change
adds, so both comments now say so and point at the feature.

`crates/agent-framework-core/src/observability.rs`,
`crates/agent-framework-core/src/observability/export.rs`; tests
`the_resource_marks_telemetry_as_agent_framework` and
`the_resource_still_carries_the_service_name` (the second a guard: the
marker must not displace the configured service name).

## Already satisfied (checked, nothing to do)

- **#9499 — merging both MCP approval lists.** Upstream's bug was an
  overwrite: setting both `always` and `never` assigned `require_approval`
  twice, silently dropping the always list. It cannot happen here —
  `agent_framework_core::tools::McpApprovalMode::into_value` builds one map
  and inserts each key independently, and
  `agent_framework_openai::responses::mcp_require_approval` then wraps each
  into the `{"tool_names": [...]}` shape the Responses API wants, merging
  both. `mcp_object_approval_mode_maps_to_tool_name_lists` already asserted
  exactly the combined output. Azure and Foundry reuse the same function via
  `tool_to_responses_spec`, so both surfaces were covered by one
  implementation — the same pattern as the embedding-error finding in the
  first pass.

## Does not apply

- **#9574 — comparing in-memory vector filters in the field's own type.**
  Upstream's fix restores Python `datetime`, `Decimal`, `timedelta` and
  `UUID` values from the strings its serializer wrote, so a filter leaf
  compares in the field's native Python type, and works around CPython
  specifics (aware-datetime equality across a repeated DST hour, exact
  decimal summation of ISO durations). The in-memory store here compares
  `serde_json::Value`s, which have no such coercion step and no distinct
  `Decimal`/`timedelta`/`UUID` types to restore. `SCOPE.md` covers this
  under *Python-runtime specifics*. If a typed-comparison gap exists here it
  is a different bug needing its own assessment, not this commit.

## Still carried forward

Unchanged from the first pass, and still the top of the queue:

- **The Redis context-scope leak.** One scope's memory can be retrieved
  under another's: the scope `TAG` fields are indexed with RediSearch's
  defaults (separator `,`, case-insensitive) and the value is written
  unescaped, so `user_id = "smith,john"` is indexed as two tags and matches
  a provider scoped to `user_id = "smith"`. Upstream's #9461 is `[BREAKING]`
  with a schema signature and a resumable migration; the smaller schema fix
  (`SEPARATOR ""` / `CASESENSITIVE`) is breaking too, since `FT.CREATE` does
  not alter a deployed index. **Still awaiting a decision** — it is not a
  change to make unilaterally.
- **AG-UI's `RUN_ERROR` events** still echo internal error text at four
  sites, the defect #9460 fixed on the DevUI surface. Upstream has not made
  that call for its own AG-UI surface.
- The remaining queued provider work (#9718, #9768, #9744, #9436) and
  workflow work (#9669, #9644), plus #9795, #9260, #9606, #9746, #9403,
  #9384, #9405 and #8920. None is a correctness defect with a wrong answer
  reaching a caller.

## Azure Rust SDK review

Written up separately in [`docs/azure-rust-sdk.md`](../azure-rust-sdk.md),
with versions read from the crates.io API rather than from announcement
posts. The headline findings:

- **Cosmos DB has shipped**, contrary to the May 2026 GA announcement that
  listed it as still coming: `azure_data_cosmos` is at **1.0.0 stable**,
  published 2026-10-22. It is the one official crate this workspace could
  usefully adopt, against roughly 1,540 of `agent-framework-cosmos`'s 5,222
  lines (`client.rs` + `auth.rs`) — behind an optional feature, as
  `entra-sdk` already does for credentials.
- **`azure_core_opentelemetry` is stable at 1.0.0**, which together with the
  resource attribute added above is most of what `SCOPE.md`'s Application
  Insights exporter gap needs.
- **There is no official Rust client for Azure AI Search, Foundry / Azure
  OpenAI, Purview or Copilot Studio.** The crate names exist and that is
  misleading: `azure_search_documents` and the `azure_analytics_purview_*`
  crates are **0.0.1 placeholders** published from the official repo in
  March 2025 and never updated (the Search one's description still says it is
  for ".NET applications"), and `azure_ai_foundry_*` is a **third-party**
  project (`github.com/bzsanti/azure-ai-foundry`, ~150 downloads), not
  Microsoft's. For those four crates the hand-rolled REST client is the only
  option, not a shortcut — worth saying plainly the next time it comes up.
- The port's existing pins are current: `azure_core` 1.1 and
  `azure_identity` 1.0 are the newest stable releases of each.
