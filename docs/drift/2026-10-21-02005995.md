## Ported this pass (4 changes, all with regression tests)

### An answer repeated after its call ran executed the call again (#9535)

`settled_approval_responses` decided settlement by two rules: a later
result for the same `call_id` settles the oldest pending response, and a
later request reusing an id supersedes the response before it. Neither
covers the transcript upstream's new test pins: an approval request,
its answer, the call's result, then **the same answer again** — a client
that resends its last answer, or a replay that repeats it. No result
follows the second copy and no request reuses its id, so it was collected
as pending and the tool ran a second time. Reproduced against the
function-invocation loop before the fix: the approved tool executed once
more on a transcript where it had already run.

Upstream's correlation tracks *requests* as well as responses, and a
response to a request that is already closed never executes; #9535 makes
that response count as settled, so replay stays inert. This port had not
carried request tracking over at all, so the fix brings it in:

- each approval request occurrence is recorded under its id (a repeat of a
  request nobody has answered yet is the same occurrence, as upstream);
- a request **closes** when a response to it is settled by a result, or
  when a result answers its call while it is still unanswered;
- a response whose id names a closed request is settled on arrival.

Only a new request reusing the id reopens it, which the existing
`a_reused_id_settled_twice_keeps_a_call_for_each_result` test still pins.
`drop_settled_approval_responses` and compaction use the same function, so
the repeated answer is also kept out of the model input.

Upstream's other new test in #9535 (`…_reclassification_does_not_execute_
without_session`) exercises its session-bound approval binding, which this
port does not have; see *Not applicable*.

`crates/agent-framework-core/src/client.rs`;
test `a_repeated_answer_to_a_closed_approval_does_not_rerun_the_tool`.

### A standing approval for `run_shell ` approved `run_shell` (#9557)

`ToolApprovalRule::tool` trimmed the tool name before storing it. A rule is
the identity of the approved tool, and `"run_shell "` and `"run_shell"`
are two different tools to the function-invocation loop, which looks tools
up by exact name. So an "always approve" given for a call to `run_shell `
became a standing approval of `run_shell`, a tool the caller never saw a
request for. The name is now kept exactly as given; an empty or
whitespace-only name is still refused.

`crates/agent-framework-core/src/harness/tool_approval.rs`;
test `rules_keep_the_exact_tool_name`.

### Two approval requests under one id were accepted (#9542)

Everything `ToolApprovalAgent` keeps is keyed by request id: an inbound
answer replaces any earlier answer with its id, and an "always approve"
choice is recorded against it. A batch carrying two live requests with one
id therefore let the answer to one stand in for the other, or dropped an
auto-approval when the caller answered its namesake. The in-box `Agent`
mints a unique occurrence id per call, but the inner agent can be any
`SupportsAgentRun`, including a remote one.

As in .NET, such a batch is now refused: the state held under the
duplicated ids (queued requests, collected answers, pending standing
approvals) is discarded and saved, so a retry cannot pick up half of the
broken batch, and the run fails with `Error::AgentExecution`. The check
runs on every outbound batch, including the pass that reaches the
auto-approval cap, where requests stream straight through: there the
second request reusing an id is refused before it reaches the caller.

`crates/agent-framework-core/src/harness/tool_approval.rs`;
tests `tool_approval_rejects_duplicate_request_ids` and
`tool_approval_rejects_duplicate_request_ids_at_the_auto_approval_cap`
(`tests/harness.rs`).

### A failed A2A task lost the reason it gave (#9534)

`task_to_chat_messages` surfaced `status.message` only for
`input-required` tasks. A task that failed, was cancelled or rejected, or
needs authorization came back as its artifacts (or its last history entry)
with the status message, which is where an A2A agent says *why*, silently
dropped. .NET now converts the status message for every state except
routine progress and success (`submitted`, `working`, `completed`) and
appends it after the artifacts; this port does the same. The last-history
fallback, which is Python's, still applies when neither artifacts nor a
status message produced anything.

Behaviour change for `input-required`: a task that carries artifacts *and*
a question now returns both, in that order, rather than only the question.

Streaming needed no change: `StatusUpdate` events already surface their
message in every state, which matches Python's intermediate-content
behaviour for streaming callers.

`crates/agent-framework-a2a/src/{agent,lib}.rs`; tests
`task_to_chat_messages_keeps_the_reason_an_unsuccessful_task_gives`,
`…_prefers_a_failure_reason_to_history` and
`…_skips_routine_status_messages`.

## Verified already satisfied

- **#9459** — decoding Ollama inline image data before serialization.
  Python's client called Ollama's native API and sliced the base64 payload
  out of the data URI by hand, so a malformed or non-image URI was sent on.
  This port talks to Ollama's OpenAI-compatible endpoint and sends the
  whole data URI as an `image_url` part through the shared OpenAI
  converter; Ollama's compatibility layer decodes and validates it.

## Not applicable, with the reason

- **#9535's session-bound half.** Upstream drops a local approval response
  unless an authoritative `AgentSession` recorded the matching request
  (from #8750), and #9535 makes that filter iterate when dropping one
  response reclassifies a mixed batch. This port never adopted the session
  binding: the function-invocation loop matches responses to the requests
  in the transcript it is given (see the 2026-10-05 pass, #8754). Whether
  to adopt it is a design question worth its own change, not a one-commit
  port; recorded under *Standing gaps*.
- **#8801** — `AgentSessionStore.DeleteSessionAsync`. There is no session
  store in this port to add a delete to. Python (`SessionStore`,
  `FileSessionStore`, experimental) and .NET both have one, so it is
  recorded as a gap below and will land with delete included.
- **MCP workflow session isolation** — still an open upstream branch
  (`fix/mcp-workflow-session-isolation`, .NET and Python halves) with a
  design proposal for workflow-owned MCP sessions (`2c895157`). Nothing
  has merged; revisit when it does.
- **#9540** — resetting compiled workflow state between runs and restoring
  shared formula state on checkpoint load. Power Fx declarative workflows:
  a recorded `SCOPE.md` boundary.
- **#9539** — validating MCP invocation headers. Headers evaluated from
  declarative workflow state; this port's MCP headers are client-level
  configuration (as recorded for #8834 on 2026-10-05).
- **#9536** — a timeout across multi-step harness file-store operations.
  The harness file store is not ported (see *Standing gaps*).
- **#9269** — preserving the caller's `CancellationToken` in memory
  providers. Rust cancels by dropping the future; there is no token to
  lose.
- **#9382** — hosted agent lifetimes and request-time agent selection for
  .NET's AG-UI hosting. Dependency-injection lifetimes with no analogue;
  the router here is constructed with its agent.
- **#9558**, **#9464** — TTL caching and pagination for MCP-listed skills.
  This port's skills have no MCP source.
- **#9563** — a .NET A2A sample.
- **Infrastructure and docs** — #9538, #9501, #9508, #9486, #9505, #9504,
  #9503.

## Go v0.2.0

Skimmed for capabilities, not commit by commit. Go's release adds
FileMemory (storage, editing and a context provider), vector data
abstractions with an in-memory connector, embedding generators with RAG
samples, a text-search context provider, vector-backed memory with Azure
AI Search, a Cosmos DB vector store, reusable harness setup with
model-call tracing, and rejecting empty outbound A2A messages.

Against this port: vector data, the in-memory store, embeddings, the
vector-backed provider, Azure AI Search and the Cosmos vector store all
exist already (`core::vectors`, `agent-framework-azure-ai-search`,
`agent-framework-cosmos`). New gaps it confirms are the **text-search
context provider** (.NET `TextSearchProvider` and Go) and **file memory**
(Python, .NET and Go). Both are added to the standing gaps.
