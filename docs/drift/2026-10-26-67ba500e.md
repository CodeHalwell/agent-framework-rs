## Ported this pass (5 changes, all with regression tests)

### `allow_multiple_tool_calls` was dropped unless a `tool_choice` was set (#8980)

`build_request` emitted `tool_choice` only inside `if let Some(tool_choice) =
&options.tool_choice`, and `allow_multiple_tool_calls` was a *parameter* of
that conversion. Anthropic exposes parallel tool use nowhere else — it is
`tool_choice.disable_parallel_tool_use` — so a caller who set
`allow_multiple_tool_calls(false)` and left `tool_choice` alone had the
setting silently discarded and got parallel calls anyway. That is the common
case: `ToolMode` defaults to unset, and the function-invocation loop stops
pinning `tool_choice` after the turn that needed it, so even a run that
started with one loses the setting on every later turn.

The setting is now carried on the API's default `auto` mode when nothing else
set a `tool_choice`. Two details beyond upstream's diff:

- it is derived **after** the `additional_properties` merge, via
  `entry().or_insert_with()`, so it is a default rather than an override: an
  explicit `options.tool_choice` and a caller's own
  `additional_properties["tool_choice"]` both still win;
- only when the request actually declares `tools`, since `tool_choice` with
  no tools is rejected by the API. As upstream, `mcp_servers` alone does not
  count.

`crates/agent-framework-anthropic/src/convert.rs`; tests
`build_request_allow_multiple_tool_calls_without_tool_choice`,
`…_true_without_tool_choice`, `…_without_tools_sends_no_tool_choice`,
`build_request_explicit_tool_choice_beats_the_derived_default` and
`…_additional_properties_tool_choice_beats_the_derived_default`.

### Bedrock never reported which model served a run (#9399)

`convert::parse_response` read `model` from nowhere, and Converse does not
echo `modelId` in its response body, so `ChatResponse::model` came back
`None` from every Bedrock call. This port was worse off than upstream
pre-fix, which at least fell back to the client's configured model: here a
per-request `ChatOptions::model` override was invisible on the response, and
so was the model itself. The streaming path derives its single update from
the same parsed response, so it was empty there too.

`parse_response` now takes the `modelId` the request was sent with — which
`get_response` already computes via `effective_model` — and prefers a
`modelId` in the body if a future API revision starts returning one.

`crates/agent-framework-bedrock/src/{convert,lib}.rs`; tests
`parse_response_reports_the_requested_model` and
`parse_response_prefers_a_model_the_body_reports`.

### A failed hosted run told the client why it failed (#9460)

`devui::run_agent` and `run_workflow` put `e.to_string()` straight into the
SSE `error` event and the 500 body. An `Error` from a run carries whatever
the failing layer put in it: a provider's raw HTTP error body, a tool's own
error text, a deserialization message naming internal types, a filesystem
path from a message store. All of it reached the caller verbatim — and the
router is served without auth unless `with_bearer_token` was set.

The caller now gets one fixed message and the detail goes to the log,
correlated by the stream's response id, with the error's compact type always
logged and its full text gated on `ENABLE_SENSITIVE_DATA` — the same gate
`agent_framework_core::observability` puts on message content, since an error
message can quote the prompt that caused it.

Upstream's other half, preserving *vetted* messages, needed nothing here:
the four sites are run failures only. The hosting layer's own validation
replies ("Pending interrupts require a resume entry…", the host and bearer
guards' messages) go through different paths and are unchanged.

**Not extended to AG-UI.** `agui.rs` puts `e.to_string()` into its
`RUN_ERROR` events at four sites — the same defect. Upstream's #9460 did not
touch its AG-UI surface, so changing it here would diverge rather than
converge, and a future upstream AG-UI change would conflict. Recorded under
*Standing gaps* for a decision rather than fixed unilaterally.

`crates/agent-framework-hosting/src/devui/mod.rs`; tests
`a_stream_that_fails_to_start_does_not_echo_the_error`,
`a_stream_that_fails_midway_does_not_echo_the_error` and
`a_failed_run_does_not_echo_the_error_in_its_500`, with a `FailingAgent`
helper in `tests/common/mod.rs`.

### A cross-site POST reached the hosted agents (#9575)

`host_guard` checked the `Host` header against an allowlist and nothing
else. That stops DNS rebinding and does not stop a browser: a page on any
origin can make the user's browser `POST
http://localhost:8080/v1/responses`, and the browser sends `Host:
localhost`, so the allowlist passes and a hostile page gets to drive every
agent the router serves.

`host_guard` is now the local-access guard upstream's `ValidateLocalRequest`
is: the allowlist, then — for a state-changing method only — a rejection of
`Sec-Fetch-Site: cross-site`, and an `Origin` that must match what the
request was addressed to. A request with no `Origin` passes: that is a
non-browser client, which is not this threat, and the allowlist already
stands between it and a rebinding attack. Both checks hang off the same
`with_allowed_hosts` / `into_secure_router` choice, since both say the same
thing about who this router is for; leaving the allowlist unset is this
port's `AllowRemoteAccess`.

Two deliberate divergences, both documented at the call site:

- **The peer address is not checked.** Upstream also requires a loopback
  remote IP. That needs `ConnectInfo<SocketAddr>`, which exists only if the
  caller serves the router with `into_make_service_with_connect_info`, so a
  middleware cannot require it without changing what `into_router` returns.
  The `Host` allowlist remains this port's stand-in.
- **The scheme is not compared**, only host and port. A server-side request
  carries no trustworthy scheme (`Host` has none, an HTTP/1.1 origin-form
  `request.uri()` has none, `X-Forwarded-Proto` is a hop's claim). It costs
  nothing: only one process can listen on a given host and port, so the
  same-authority page over the other scheme does not exist to attack from.

The bearer check was hardened in the same file while it was open:
`fixed_time_eq` replaces `==` on the token (the equivalent of .NET's
`CryptographicOperations.FixedTimeEquals`, which upstream's validator uses,
and like it leaking only the length), and the scheme is matched
case-insensitively with the credential trimmed, per RFC 7235 and upstream.

`crates/agent-framework-hosting/src/security.rs`; eight tests in
`tests/security.rs` covering the cross-site rejection, same-origin and
matching-origin acceptance, origin mismatches, `GET` being untouched, and
the bearer scheme.

### Tool-invocation metrics were missing three dimensions (#9592)

Upstream found it was copying span attributes wholesale onto the
function-invocation histogram, which put a tool's arguments and result — and
so prompt content — into metric dimensions, and replaced that with an
explicit set. This port has always built the list by hand and never carried
those, so the leak never existed here; but its list was
`agent_framework.function.name` plus `error.type`, where upstream's is
`gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`,
`gen_ai.tool.type=function` and the measurement tag. The three missing
dimensions are added, which is the point of the shared constants: the same
dashboard has to read both languages' output.

`crates/agent-framework-core/src/observability.rs`; test
`function_invocation_duration_dimensions_match_upstream`, which asserts the
dimension set exhaustively, so a dimension upstream does not emit — or one
carrying tool content — fails here.

## Verified already satisfied

- **#9491** — the assistant role on streamed Gemini updates. Python built
  role-less updates, so a text update after a tool call was appended to the
  tool message and then dropped by its own serializer.
  `gemini::convert::stream_chunk_to_update` has always set
  `role: Some(Role::assistant())`.
- **#9469** — stateless shell tools inheriting the host's stdin, which let a
  model-chosen `cat` steal a CLI agent's approval input. Every spawn in
  `shell/{process,docker}.rs` already sets `Stdio::null()`.
- **#9476** — passing a stream's terminal error into nested streams when
  closing them. The bug it fixes is behavioural, not just plumbing: a failed
  or cancelled Python `ResponseStream` ran its *success* cleanup, so every
  `ContextProvider.after_run` fired as though the run had worked and the
  partial turn was saved to history. Here `ContextProvider::after_run` takes
  the terminal error as an explicit `Option<&Error>` argument, and
  `ChatAgent`'s streaming path passes `Some(&e)` on a mid-stream failure —
  taking the completion state out of the `finish` cell as it does, so the
  success path cannot also run (`agent.rs`, the `Some(Err(e))` arm). Nothing
  records a failed turn as a good one.
- **#9472** — recommending `include_detailed_errors=True` in a tool-failure
  warning only when it is off. This port logs no such warning:
  `include_detailed_errors` only shapes the `FunctionResultContent` exception
  text the model is given (`client::tool_error_message`). There is no message
  to make conditional.
- **#9588** — retiring the Azure Persistent v1 live integration tests while
  keeping the package. Not a change to port, but it confirms the direction
  this port already took: the Azure AI Agents threads/runs data plane was
  dropped in favour of the Foundry Responses API (see PARITY's Foundry row).

One Azure gap this window surfaced, added to `SCOPE.md`: **a session store
backed by Azure storage**. `Microsoft.Agents.AI.Hosting.AzureStorage` ships
`AzureBlobAgentSessionStore : AgentSessionStore` with
`SaveSessionAsync`/`GetSessionAsync`/`DeleteSessionAsync`, and Foundry
Hosting ships file-system, in-memory and Foundry-backed stores against the
same abstraction. The abstraction itself is no longer the blocker — 0.14.0
ported it as `core::session_store`, with in-memory and file-system
implementations — so this is now an implementation against a trait that
exists, and `agent-framework-azure` already carries the Entra credential
chain and `azure_http_client` it would need. Recorded, not started.

On the codependency question that goes with it: the official **Azure SDK for
Rust** is already wired in. `azure_core` 1.1 and `azure_identity` sit behind
`agent-framework-azure`'s optional `entra-sdk` feature (the workspace
`Cargo.toml` documents why `reqwest_rustls` is mandatory there), and the data
planes — Azure OpenAI, Cosmos NoSQL REST — are hand-rolled deliberately. For
the blob store above, `azure_storage_blob` **1.1.0** is published on the same
`azure_core` 1.x line, so adopting it adds no second `reqwest` major beyond
the one `entra-sdk` already accepts, and the existing `TokenCredential` work
carries over. A hand-rolled alternative is also small — save/get/delete is
one `PUT`/`GET`/`DELETE` against a blob URL, which `azure_http_client`
already signs. Either way the choice is about dependency weight, not missing
capability.

Also worth recording because it closes a line `SCOPE.md` had carried: Cosmos
chat history is **no longer** coupled to its partition-key strategy. 0.14.0
landed upstream #9214 in full — `with_tenant_id`/`with_user_id` write
`tenantId`/`userId` on every document whatever the partitioning, and
`CosmosPartitionStrategy` chooses `threadId` or the hierarchical
`tenantId`/`userId`/`threadId` key. The stale clause is removed from
`SCOPE.md`.
