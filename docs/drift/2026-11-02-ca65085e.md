## Ported this pass (5 changes, all with regression tests)

### Gemini never reported which model served a run (#9736)

`convert::parse_response` read `model` only from the body's `modelVersion`,
and Gemini omits that field from some responses, so `ChatResponse::model`
came back `None` — and a per-request `ChatOptions::model` override was
invisible on the response. `parse_stream_chunk` had the same gap on every
chunk.

This port was worse off than upstream pre-fix, which at least fell back to
the client's configured model on the streaming path. Here *neither* path had
a fallback, so both were empty. It is the same defect class as the Bedrock
`modelId` fix ported last pass (#9399).

Both functions now take the `requested_model` the request was sent to — the
model id `build_body` already resolves, since for this API the model is a URL
path segment rather than a body field — and prefer a `modelVersion` in the
body when one is present. One detail beyond upstream's diff: on the
streaming path the fallback is applied **after** the "carries nothing new"
test, so a keep-alive chunk still parses as `None` instead of becoming an
update that carries only a model label.

`crates/agent-framework-gemini/src/{convert,lib}.rs`; tests
`parse_response_reports_the_requested_model_when_the_body_omits_one`,
`parse_response_prefers_the_model_the_body_reports`,
`parse_stream_chunk_reports_the_requested_model_when_the_chunk_omits_one`,
`parse_stream_chunk_prefers_the_model_the_chunk_reports` and
`a_requested_model_alone_does_not_make_an_empty_chunk_an_update`. The two
"reports the requested model" tests fail pre-fix; the other three are guards
that must hold either way.

### A round cap of 0 ended a run before it began, in two orchestrators (#9502)

Both Magentic and group chat check the round limit *before* incrementing the
round counter, so an uncoerced `0` short-circuits the loop on its first pass:
no progress ledger is requested, no participant speaks, and the caller gets
only the "Stopped due to round limit" placeholder.

Upstream's base group-chat orchestrator has coerced a cap below 1 up to 1
since it was written (`_base_group_chat_orchestrator.py`:
`max(1, max_rounds)`), and #9502 brings Magentic into line with it. Here
**neither** orchestrator coerced, so both were affected — group chat's gap
predates the upstream commit that prompted the look.

Magentic coerces in `MagenticBuilder::build` rather than in the
`max_round_count` setter, because the cap can also arrive from a custom
`MagenticManager`'s `max_round_count()`, which a setter would never see.
Group chat coerces where it already applies its default.

`crates/agent-framework-core/src/workflow/orchestration/{magentic,group_chat}.rs`;
tests `a_round_cap_below_one_is_coerced_to_one` in both
`tests/orchestration_magentic.rs` and `tests/orchestration_group_chat.rs`.
Both fail pre-fix.

### A workflow-as-agent lost its usage and leaked internal messages (#9720, #8729)

`WorkflowAgent::outputs_to_messages` recognised two output shapes — a
`Vec<Message>` and a single `Message` — and passed everything through
unfiltered. Two defects followed, and they are upstream's two commits:

- **An `AgentResponse` output was not recognised at all** (#9720). It fell
  through to the catch-all arm and was stringified via `other.to_string()`,
  so a child agent's response arrived as one assistant message containing
  raw JSON, and its `usage_details` were discarded. `AgentResponse` was
  built with `..Default::default()` besides, so a workflow-as-agent reported
  no usage from *any* run.
- **Non-assistant messages reached the caller** (#8729). A system prompt and
  a tool result are internal workflow artifacts, and a user message gets
  re-emitted — a group-chat orchestrator yields the whole conversation, the
  caller's own turn included.

`outputs_to_messages` now tries `AgentResponse` first, takes its
caller-facing messages and merges its `usage_details`, and filters both
message shapes through a new `is_caller_facing`. `run` reports the merged
usage. Usage merges even when every message of the response was filtered
out: the tokens were billed either way.

The shape order is unambiguous rather than lucky: `AgentResponse::messages`
carries no serde default, so only an object with a `messages` array parses
as one, and a bare `Message` has no such field.

Two notes on how `is_caller_facing` differs from upstream's
`_caller_facing_messages`:

- upstream also exempts a call flagged `informational_only` — a hosted call
  recorded for transcript fidelity that never gets a local result. There is
  no such flag here, and none is needed: a provider-hosted MCP call is its
  own `Content::McpServerToolCall` variant rather than a
  `Content::FunctionCall`, so it is already not an envelope.
- the pending-request messages `request_message` builds also carry a
  `Content::FunctionCall`, but `run` appends them *after* this filter has run
  over the workflow's outputs, so surfacing an outstanding request is
  unaffected. `workflow_agent_surfaces_pending_request_info` covers it.

`crates/agent-framework-core/src/workflow/orchestration/workflow_agent.rs`;
tests `an_agent_response_output_carries_its_usage_up`,
`an_agent_response_output_carries_usage_even_with_no_caller_facing_message`,
`non_assistant_output_messages_are_not_returned_to_the_caller` and
`an_assistant_message_holding_a_function_call_is_dropped_whole`. All four
fail pre-fix.

### The Foundry chat client could not bound a request (#9699)

`FoundryChatClient` had no timeout control, and `reqwest` applies none by
default, so a hung Foundry endpoint stalled a run indefinitely with no way
to say otherwise. This port was worse off than upstream pre-fix, which at
least inherited the OpenAI SDK's own defaults (5s connect, 600s total);
there is no such default here, which makes the setting worth more.

`FoundryChatClient::with_timeout(Duration)` sets a total per-request
timeout. It is backed by a new
`agent_framework_azure::azure_http_client_with_timeout`, a sibling of the
existing `azure_http_client` sharing one builder, so the whole Azure crate
family can reach it rather than only Foundry.

Two details worth stating:

- the bound spans the whole request, body included, so on
  `get_streaming_response` it caps the lifetime of the stream rather than the
  time to first token. The doc comment says so, and recommends a generous
  value or none when streaming long answers.
- `with_timeout` rebuilds the underlying HTTP client, which is also what
  carries this crate's `User-Agent`. Rebuilding it without that header would
  re-attribute Foundry traffic to `agent-framework-azure` — exactly what
  `http_client()` exists to prevent — so a timed client is tested for it.

It applies to this chat client only; `FoundryEmbeddingClient` and
`FoundryMemoryProvider` build their own clients and are unchanged, as
upstream's are.

`crates/agent-framework-azure/src/lib.rs`,
`crates/agent-framework-foundry/src/lib.rs`; tests
`a_request_that_outlives_the_timeout_fails_instead_of_hanging`,
`the_same_slow_response_still_succeeds_with_no_timeout_set` and
`a_timed_client_still_sends_the_foundry_user_agent`, with a
`FakeServer::start_with_delay` helper. The first fails pre-fix (the method
did not exist); the second is the guard proving it is the bound that ends the
request and not the fake server being broken.

The timeout test asserts on *when* the request gave up, not on the error
text: `reqwest`'s message here is the opaque "error sending request for url
(...)", which does not distinguish a timeout from a refused connection.
Improving that wording is a separate change and is recorded under *Standing
gaps*.

### MCP approval policies had no default for unlisted tools (#9828)

Upstream added a `default` key to `MCPSpecificApproval`, resolving a tool in
order: the always list, the never list, `default`, then no approval.

`McpApprovalMode::PerTool` carried only an `always_require` set, with a doc
comment explaining why the never list was dropped: Rust's `ApprovalMode` has
no unset state, unlike Python's, so "explicitly never" and "not listed" both
collapsed to `NeverRequire` and the list carried no information. **A
`default` makes that reasoning obsolete** — with a `default` of
`AlwaysRequire`, the never list is the only way to express "approve
everything *except* these", which is the configuration the upstream key
exists for.

`PerTool` now carries `never_require` and `default` alongside
`always_require`, and `resolve` follows upstream's order. The practical
value is the inverse policy: `per_tool_except(["read_file"])` gates a tool
the server adds later, or that a reload brings in, instead of letting it
through unapproved. `with_default` and `with_never_require` compose onto a
`per_tool` policy; both are no-ops on the whole-server variants, which
already answer for every tool.

`per_tool`'s existing behaviour is unchanged (empty never list, no default),
so no caller's policy shifts under them.

**Two parts of #9828 do not apply.** Upstream also normalises a name list
given as a single string into one name rather than a substring pattern — a
`str`/`Sequence[str]` ambiguity that a typed `IntoIterator<Item = &str>`
cannot express. And it warns at construction when `never_require_approval`
is set without `default`, because that fallback may change in a future
release; here the lists are enum fields rather than validated constructor
arguments, and there is no constructor to hang a once-per-construction
warning on.

`crates/agent-framework-mcp/src/tool.rs`; tests
`a_default_decides_the_tools_in_neither_list`,
`the_always_list_is_checked_before_the_never_list`,
`the_never_list_is_checked_before_the_default`,
`no_default_still_falls_back_to_never_require` and
`a_default_is_a_no_op_on_the_whole_server_modes`.

Note this is the *client-side* MCP policy
(`agent_framework_mcp::McpApprovalMode`). The hosted connector's
`agent_framework_core::tools::McpApprovalMode` is a wire representation the
service resolves, already carries both name lists, and is untouched: a
`default` there would need the service to accept one.

## Azure-ecosystem review

### A scope value containing a comma can leak memory across scopes (Redis)

**This is the most serious finding of the pass, and it is not fixed here.**

`agent-framework-redis`'s context provider declares its `TAG` scope fields
(`application_id`, `agent_id`, `user_id`, `thread_id`, …) with RediSearch's
default options, which means separator `,` and case-insensitive matching. The
stored JSON value is written raw by `JSON.SET`; `escape_redisearch` is
applied only when *building the query string*, never to what is indexed.

So a scope value containing a comma is indexed as two separate tags. A
provider scoped to `user_id = "smith"` issues `@user_id:{smith}` and matches
an entry stored under `user_id = "smith,john"` — one user's memory is
retrieved under another user's id. Case-insensitivity conflates `"Alice"`
and `"alice"` the same way, less severely.

Escaping does not help: the split happens at index time, on the unescaped
value, and query-syntax escaping cannot undo it. The SCAN fallback path is
unaffected — it compares scope values exactly, client-side — so this is
specific to the RediSearch (`FT.SEARCH`) path.

This is the defect upstream's **#9461** fixes, and its approach is
instructive: it stops storing scope values as tags at all, hashing each into
an opaque `af_scope_v1_<field>` sha256 token. A hex token contains no
separator and is case-stable, which sidesteps the schema question entirely —
and that is why upstream shipped it as `[BREAKING]`, with a schema signature
check and a resumable migration for existing indices.

Two ways to fix it here:

1. **Follow upstream**: hashed scope tokens, new field names, and a
   migration for data already indexed.
2. **Declare the schema correctly**: `SEPARATOR ""` and `CASESENSITIVE` on
   the scope `TAG` fields. Far smaller, but `FT.CREATE` does not alter an
   existing index, so every already-deployed index keeps the old behaviour
   unless it is dropped and rebuilt — the same migration problem, with less
   of upstream's thinking behind it.

Neither is a change to make unilaterally at the end of a pass: both are
breaking, both need a migration story, and option 2 rests on an
`FT.CREATE` option this pass could not exercise against a real server (the
Redis tests are hermetic fakes). Recorded for a decision, and it should be
the next pass's first item.

### `agent-framework-copilotstudio` sends no framework `User-Agent`

`CopilotStudioAgent` builds a bare `reqwest::Client::new()`
(`src/agent.rs:60`) and the crate has no `agent-framework-azure` dependency,
so its traffic to a Microsoft Power Platform endpoint carries no
`agent-framework-rust/<version>` header and is invisible to Azure's
telemetry and supportability tooling.

`SCOPE.md`'s standing "framework `User-Agent` outside the Azure crates" item
names `agent-framework-purview` and `agent-framework-foundry-local`, but not
this crate — it was missed when that note was written, and Copilot Studio is
as much a Microsoft-service-facing connector as the other two. `SCOPE.md` is
updated to name it.

Cheap to fix in isolation (take the `agent-framework-azure` dependency for
`azure_http_client`), but it pulls a credentials-and-Responses-client crate
in for one header, which is the same trade-off that has kept the general
item open. Left with the standing item rather than solved crate-by-crate.

## Standing gaps

Carried forward, plus what this pass added:

- **AG-UI still echoes internal error text.** `agui.rs` puts
  `e.to_string()` into its `RUN_ERROR` events at four sites — the defect
  #9460 fixed on the DevUI surface last pass. Upstream's #9460 did not touch
  its AG-UI surface, so changing it here would diverge. Unchanged this pass;
  still awaiting a decision.
- **Redis scope identity** — see the Azure review above. New, and the most
  serious item on this list.
- **`agent-framework-copilotstudio`'s missing `User-Agent`** — see the Azure
  review; folded into `SCOPE.md`'s existing item.
- **A zero `Duration` MCP request timeout** fails every request immediately
  rather than being rejected (#9314). Fixing it means making the
  `request_timeout` / `timeout` builder setters fallible, which is a
  breaking API change for a footgun no caller has hit.
- **`reqwest`'s opaque transport errors.** A timeout, a refused connection
  and a DNS failure all surface as "request failed: error sending request
  for url (...)" through the Azure clients. Distinguishing them (via
  `reqwest::Error::is_timeout` / `is_connect`) would make a hung endpoint
  diagnosable from the error alone, which the Foundry timeout test had to
  work around by measuring elapsed time instead.
