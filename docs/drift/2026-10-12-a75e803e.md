## Ported this pass (6 changes, all with regression tests)

### The Magentic progress ledger counted braces inside strings (#9089)

`first_balanced_object` scanned for the first balanced `{...}` span without
tracking string state, so a ledger answer that mentioned a brace — "the
f-string is missing its closing `}`", a snippet in an instruction — closed
the object at that brace. The span was then invalid JSON, the parse failed,
and the round stalled on output that was perfectly well formed.

The scan now tracks string and escape state, so only braces outside strings
move the depth. Three cases are covered (a brace in prose, a stray `{`, an
escaped quote followed by a brace), plus a nested object to pin that braces
outside strings still count and an unterminated string to pin that it is
still an error.

`crates/agent-framework-core/src/workflow/orchestration/magentic.rs`.

### Handoff tool names had no length cap (#9035)

Upstream added two things to `get_handoff_tool_name`: sanitizing characters
providers reject, and cutting the name to 64 characters. The first half was
already here and stricter than upstream's regex — `sanitize_identifier`
collapses runs, trims, lowercases, handles an empty result and a leading
digit. The cap was missing, so a participant named "Specialist Agent For
Extremely Detailed Billing And Invoicing Questions" produced an 82-character
tool name and OpenAI, Anthropic and Gemini each rejected the whole request.

Naively truncating would have broken routing. The coordinator resolves a
handoff by stripping the `handoff_to_` prefix from the called tool and
looking the remainder up in `tool_targets`, whose keys were built from the
*untruncated* sanitized name — so a cut name would have resolved as an
unknown target. Both the tool spec and the lookup table are now built
through one `handoff_tool_name`, and the cut segment is a key, so a cut
participant still routes. Two participants that collide once cut are
rejected by `HandoffBuilder::build` rather than silently sharing a tool,
which would leave one of them unreachable.

`handoff_tool_name` is exported, since a caller attaching marker tools by
hand needs the same name the coordinator will resolve.

`crates/agent-framework-core/src/workflow/orchestration/handoff.rs`.

### A blank `AZURE_OPENAI_API_VERSION` built a malformed URL (#9098)

Upstream's fault was precedence: it passed `api_version or
default_azure_api_version` into `load_settings`, and an explicit value there
beats the environment, so `AZURE_OPENAI_API_VERSION` was never read and
every Azure request used the hard-coded default. That cannot arise here —
`from_env` reads the variable and `with_api_version` applies over it, which
is the right order already.

Reading it surfaced a different fault on this side. Both the chat and
embeddings clients forwarded the variable *verbatim*, including when it was
set but blank, producing `...?api-version=`. Chat Completions and the
embeddings route both require the parameter, so that is a 400 rather than a
service default. Blank now leaves the dated default in place, which is what
upstream's post-fix `if not azure_settings.get("api_version")` does with an
empty string.

Whitespace-only counts as blank too. That is a small deviation — upstream
would forward `" "` — and the better behaviour: a whitespace api-version is
a broken request under either reading.

The Responses client is deliberately untouched. There a blank value opts out
of the query parameter entirely, which its GA v1 route accepts, and that
difference is documented at both ends.

Both `from_env` implementations were split into a `from_env_vars(get)` form,
matching the Responses client, so the new tests exercise an in-memory map
instead of the process-global environment.

`crates/agent-framework-azure/src/{lib,embeddings}.rs`.

### Data URI parsing: a missing default and an accepted encoding (#8918)

Upstream rewrote data-URI handling around one shared parser. Most of that
is already the shape here, and two parts were not:

- **An omitted media type** (`data:;base64,...`) read as an empty string.
  RFC 2397 gives it `text/plain`, which is what upstream now returns. An
  empty string is unusable to every converter that switches on the type.
- **A second bare encoding marker** was accepted.
  `data:text/plain;gzip;base64,AAAA` passed, because the check was
  `strip_suffix(";base64")` on the header and `gzip` simply ended up inside
  the part read as the media type. The payload would then be decoded as
  plain base64 and the caller handed mangled bytes. Parameters between the
  media type and the marker must now be `name=value` pairs; a second bare
  token is refused.

Upstream's magic-number hardening in the same commit (BMP header size, SVG
word boundaries and BOM, MP3 frame-sync bits) has no analogue: this port
reads the declared media type and does not sniff payload bytes.

`crates/agent-framework-core/src/types/content.rs`.

### Bedrock dropped reasoning content, so extended thinking broke on tool calls (#8936)

Surfaced by triaging upstream's streamed-reasoning fix, whose streamed half
does not apply — this client aggregates a single `Converse` call rather than
speaking `ConverseStream`, a boundary `SCOPE.md` records. The non-streaming
half turned out to be a real and total gap: `parse_content_block` decoded
only `text` and `toolUse`, and `content_to_block` mapped reasoning to
nothing, so `reasoningContent` was dropped on the way in and again on the
way out.

Converse checks an assistant turn's reasoning against its signature. A
follow-up turn after a tool result therefore arrived carrying a `toolUse`
whose thinking was gone, and the request failed — extended thinking worked
only as long as no tool was involved.

Both directions now carry it. A `reasoningText` block becomes reasoning
content with its signature in `protected_data`; a `redactedContent` blob,
which has no text or signature to rebuild from, keeps the original block in
`raw_representation`; either is replayed byte for byte. Reasoning that did
not come from Converse needs both text and a signature to be sent, because
Converse refuses a `reasoningText` block without one, so unsigned reasoning
from another provider is dropped rather than sent in a shape the service
rejects.

`crates/agent-framework-bedrock/src/convert.rs`.

### The port did not identify itself to Azure (review-surfaced, cites #9223)

Upstream added a dedicated `agent-framework-azure-cosmos-memory` User-Agent
token this window, so Cosmos requests name both integrations. The memory
provider it lands on is not ported — it is blocked on the Agent Memory
Toolkit — but checking it answered a broader question badly: **no client in
this workspace sent a `User-Agent` at all.** Azure saw bare `reqwest`
traffic.

That matters beyond cosmetics. Azure reads the header for service telemetry,
throttling diagnostics and supportability; a request that sends none is
traffic the platform, and anyone reading a support case, cannot attribute to
the framework. Both upstream runtimes identify themselves, per package.

`agent_framework_azure::azure_user_agent` formats one token pair —
`agent-framework-rust/<version> (<component>)` — and `azure_http_client`
builds a client carrying it. Each Azure-facing crate wires its constructors
through a crate-local `http_client()` passing its own `CARGO_PKG_NAME` and
`CARGO_PKG_VERSION`, so a request names both the framework and the connector
inside it and the format lives in one place: the Azure OpenAI chat,
embeddings and Responses clients, the Cosmos REST client, Azure AI Search
(provider and vector store), and Foundry (embeddings and memory).

The Cosmos loopback suite asserts the header on the wire, so the plumbing is
covered end to end rather than only at the formatter.

## Verified already satisfied

Read against the Rust code rather than classified by package path:

- **#9056** — A2A empty attachment payloads. Upstream relaxed a regex from
  `+` to `*`; `data_uri_payload` splits on `";base64,"` and returns whatever
  follows, so an empty payload was always accepted.

  `skip_serializing_if = "Option::is_none"`, so a null never reaches a hash.

  session to clear.

## Standing gaps

- **Azure Cosmos DB chat metadata vs. partition strategy** (#9214). The
  `.NET` provider decoupled the two: tenant and user IDs are persisted
  whenever set, and a `PartitionKeyFactory` delegate chooses the key, so
  flat `/conversationId` partitioning no longer costs you the metadata.
  `CosmosChatMessageStore` here partitions by `threadId` alone and has no
  tenant/user concept, so there is nothing yet to decouple — the module docs
  already record single-level partitioning as a deliberate simplification.
  Tractable, and more so than it looks: `partition_key_header_value` already
  serializes a JSON array, which is exactly the hierarchical header format,
  and `create_container` already takes the key path as a parameter. What it
  needs is optional tenant/user fields on the store, those fields on the
  document whatever the strategy, multiple paths at container creation, and
  the right key values threaded through every read, write, query and delete.
  It is an API addition, so it wants its own change rather than a corner of
  a drift pass.
- **Handoff per-agent autonomous turn limits.** Upstream's
  `with_autonomous_mode(agents=[...], turn_limits={...})` is per participant,
  and #8965 this window fixed an explicit `0` being swallowed into the
  default of 50. Here the knob is a single `HandoffBuilder::max_iterations`
  cap plus a global `HandoffInteractionMode`, where `Autonomous` already
  means "complete on the first non-handoff answer" — upstream's `0`. So the
  bug cannot arise, but the per-agent surface is genuinely absent, and
  `max_iterations(0)` clamping to 1 is currently undocumented.
- **Multimodal embedding inputs** (carried from last pass).
  `EmbeddingClient::get_embeddings` takes `Vec<String>`, so upstream's image
  and media embedding inputs cannot be expressed. Widening the trait affects
  every embedding client.
- **`User-Agent` beyond the Azure crates.** The non-Azure provider clients
  (OpenAI, Anthropic, Gemini, Ollama, Mistral, Bedrock, MCP, A2A, mem0)
  identify themselves no better than the Azure ones did. The helper now
  exists but lives in `agent-framework-azure`; a framework-wide header wants
  it somewhere every crate can reach, and `agent-framework-core` carries no
  `reqwest` dependency by design.
