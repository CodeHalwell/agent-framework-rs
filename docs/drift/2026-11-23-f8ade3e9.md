## Assessed, not ported (2 changes)

### Serving one agent per Foundry hosting container is already the shape here (.NET #10328)

Upstream's `[BREAKING]` change: Foundry publishes a dedicated endpoint per
hosted agent, so a container now serves exactly one agent, passed to
`AddFoundryResponses` as an instance or a factory. The agent is no longer
registered in or resolved from DI, and `agent.name`, `model` and
`metadata["entity_id"]` no longer select among several.

This port never had the surface the change removes. `ResponsesHostServer`
takes exactly one target at construction —
`ResponsesHostServer::agent(Arc<dyn SupportsAgentRun>)` or
`::agent_factory(...)` (`crates/agent-framework-foundry-hosting/src/responses.rs:393`,
`:398`) — stored as a single private `Target`
(`responses.rs:323`). There is no registry to resolve from and no
request field that selects an agent: `config.agent_name`
(`config.rs:44`, read from `FOUNDRY_AGENT_NAME`) is span and session
identity only, never a lookup key. "A second `AddFoundryResponses` call
throws" has no analogue either, because a second call here would be a
second server value.

The two lifetimes also already match. `Target::Agent(agent) =>
agent.clone()` reuses one instance for every request, and
`Target::AgentFactory(factory) => factory().await?` builds a fresh agent
per request (`responses.rs:1684`, `:2219`, `:2916`) — upstream's
instance/singleton and scoped/transient cases respectively. Rust's
ownership handles the disposal half: a per-request agent drops when the
run's `Arc` goes out of scope.

The commit's other two parts do not apply:

- **Reading sessions saved under the legacy `key:{name}` identity.** A
  migration read-fallback for records written by .NET releases through
  1.28.0. `session_item_key` is documented as this host's own format —
  the JSON array `[agent id, session id, {partitions}]` — and upstream's
  `FoundryAgentSessionStore` keys by bare session id, so the two never
  shared records and there is nothing to migrate from
  (`sessions.rs:24-33`, which already says so).
- **The leaked `OpenTelemetryAgent` wrapper per response.** A real .NET
  defect: each wrapper registers a `Meter` and an `ActivitySource` in
  process-wide lists until disposed. This port has no telemetry wrapper
  *agent* at all — foundry-hosting emits `tracing` spans directly
  (`host.rs:372` is its only OpenTelemetry reference), so there is no
  per-response object to leak and no need for upstream's new
  `RequireOpenTelemetryAgent` guard.

### Bounding declarative HTTP response reads has no landing site (.NET #10344)

Upstream capped `DefaultHttpRequestHandler` response bodies at 10 MiB
after decompression, validated the buffered length, preserved bodyless
`HEAD`/`304` responses and fixed cancellation through decoding.

`DefaultHttpRequestHandler` is the HTTP *action* of the declarative
workflow runtime — the Power Fx / Copilot Studio DSL that
[`SCOPE.md`](../../SCOPE.md) records as out of scope.
`agent-framework-declarative` contains no HTTP code whatsoever (no
`reqwest` import, no `http` reference in the crate's sources); it loads
agent manifests and a Rust-native `WorkflowSpec`, neither of which can
issue a request. There is no handler to bound.

The *class* of defect was checked more widely rather than dismissed with
the scope citation alone, because an unbounded body read is a
memory-exhaustion vector wherever it sits. Across the workspace there are
51 unbounded `.text()`/`.bytes()`/`.json::<…>()` response reads, but every
one of them targets an endpoint the **operator** configured — a provider
API, a storage account, an MCP server, an AG-UI or A2A peer. None takes its
URL from a model, a workflow author or a request body, which is exactly
what makes upstream's handler need a cap: its URL comes from the workflow
definition and is only host-allowlisted. The port also ships no HTTP or
web-fetch tool (`agent-framework-tools` is `lib.rs` plus `shell`), so there
is no model-chosen fetch either.

One case deserves naming, so the claim above is not read as broader than it
is. In A2A a fetched URL is not literally operator-typed: `get_agent_card`
adopts the peer's declared `card.url` (and then the extended card's `url`)
as the RPC endpoint, so later calls — carrying this client's configured auth
headers — go to a host the remote card chose
(`crates/agent-framework-a2a/src/client.rs:176`, `:182`). That is the A2A
spec's own design (the card declares its service URL), the behaviour matches
upstream and the `a2a-sdk` reference package the doc comment cites, and
discovery itself is correctly reduced to the origin per the spec
(`client.rs:150-159`). Conformant, not a defect.

Nothing to port, then — recorded so the next pass need not re-derive it.

## Findings (4, all now in `SCOPE.md`)

This pass's real output. The method: cross-check **all 44** upstream Python
packages against the 31 crates and `SCOPE.md`, rather than diffing the
window alone — which is what surfaced the first three, none of which
originates in this window. `SCOPE.md`'s own rule ("Anything not listed is
in scope") is what makes an unrecorded package a defect rather than a
footnote.

The packages that do map, and where: `ag-ui` →
`agent-framework-hosting/src/agui`, `hosting-a2a` → `hosting/src/a2a.rs`,
`hosting-responses` → `hosting/src/responses.rs` and `openai_compat.rs`,
`orchestrations` → `core/src/workflow/orchestration`,
`azure-contentunderstanding` → `agent-framework-azure`, `azure-cosmos` →
`agent-framework-cosmos`. The rest match a crate by name or an existing
exclusion.

1. **The port cannot expose an agent as an MCP tool, and nobody had noticed.**
   The one missing *capability* this pass found, and the reason the
   package-level cross-check was worth doing. `agent-framework-mcp` is an
   MCP **client** — the README says so — and upstream's `hosting-mcp` is the
   inverse direction: `mcp_to_run`, `mcp_from_run`, `AgentMCPTool` and
   `WorkflowMCPTool`, which generate a native MCP `Tool` definition from an
   agent or a workflow and convert arguments and results both ways. There is
   no equivalent here, so an agent built with this port can consume MCP
   servers but cannot be served to an MCP client.

   It is not new drift: `hosting-mcp` landed upstream on **2026-09-17**, and
   roughly nine passes since (2026-09-21 through 2026-11-16) read the name
   as covered by `agent-framework-mcp` — the opposite direction. That is the
   failure mode of diffing a window instead of the package list, and it is
   why this pass checked all 44.

   Scoping it, since the entry should not overstate the cost: upstream
   deliberately owns no server lifecycle and picks no web framework, so the
   work is conversion plus tool-definition generation, not protocol work.
   The types are already public (`ContentBlock`, `CallToolResult` in
   `agent-framework-mcp/src/protocol.rs`), and the serving direction has
   been written once already — `agent-framework-claude`'s private
   `ToolServer` (`src/mcp.rs`, `list`/`handle`/`call`) answers MCP JSON-RPC
   for the Claude CLI's `sdk` server contract, and
   `examples/mcp/mcp_http_transport.rs` hand-rolls ~60 lines of axum as a
   fixture. Neither is reusable, but both show the shape.

2. **Oracle was cited as a recorded boundary that did not exist.** The
   2026-10-12 pass listed #8676 and #9233 among "recorded `SCOPE.md`
   boundaries". `SCOPE.md` had no Oracle entry, so for six weeks the
   connector was neither ported nor excluded while a pass record implied it
   had been ruled out. Now recorded under *Not yet ported* with the actual
   constraint: no comparable Rust driver (`oracle` 0.6.3 and `sibyl` 0.7.1
   are OCI bindings needing Oracle Instant Client, a C library, at build and
   run time; of the three Oracle crates on crates.io only `oracle-rs` 0.1.7
   is pure Rust, and it is still 0.1.x) and no Oracle AI Database 26ai in CI to verify against.
3. **NVIDIA was deferred as "a scope decision" that was never taken.** The
   2026-11-02 pass triaged #8920 with "adding one is a scope decision, not
   drift" and left it there. Now recorded under *Not yet ported*, with what
   it would cost: upstream's client is embeddings-only over NVIDIA's
   OpenAI-compatible NIM endpoint, so here it is a thin crate over
   `agent-framework-openai`'s embedding client plus input batching and the
   two out-of-schema options (`input_type`, `truncate`).
4. **The "injected client wins over connection settings" series is
   settled.** The 2026-11-16 pass queued twelve upstream PRs (#9982, #9983,
   #9985, #9984, #9987, #9991, #9993, #9996, #9999, #9969, #9967, #9977) as
   "plausibly N/A throughout — but that is an assumption worth one
   deliberate check rather than twelve guesses, and it should be settled
   once and recorded in `SCOPE.md`." Checked and settled: this port uses
   **disjoint constructors**. A store or client is built either from
   resolved settings (`from_env`, or an explicit endpoint/key) or from a
   client the caller already holds (`from_client`) — verified on
   `agent-framework-mongodb` (`lib.rs:1180`, `:1193`),
   `agent-framework-postgres` (`:1042`, `:1049`) and
   `agent-framework-azure-documentdb` (`:1356`, `:1366`). Upstream's bug is
   that a single constructor accepts both and silently preferred the
   settings; there is no code path here in which both apply and one must
   win, so the series cannot arise. Recorded under *Expressed differently*.

Also fixed in passing: `ALIGNMENT_PROGRESS.md` still read
`ca65085e` (2026-11-01). The 2026-11-16 pass advanced the baseline in
`docs/drift/README.md` but not there, so the two files disagreed by a
fortnight. Both now read `f8ade3e9`.
