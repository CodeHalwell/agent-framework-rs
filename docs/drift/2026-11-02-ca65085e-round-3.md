## Ported: Anthropic server-tool replay and `pause_turn` continuation (#9718)

Anthropic's *server* tools — web search and web fetch — run on the API's
side. A response carries the call (`server_tool_use`, id prefixed
`srvtoolu_`) and its result (`web_search_tool_result` /
`web_fetch_tool_result`) inline in the assistant turn, followed by the
answer. Two things were wrong with how this port handled that.

### Every follow-up after a web search was refused

`parse_content_blocks` turns those blocks into a `FunctionCall` and a
`FunctionResult`, which is reasonable on the way in. On the way back out,
`messages_to_anthropic` had no notion of a server tool, so the turn
replayed as:

```json
{ "role": "assistant", "content": [
  { "type": "tool_use",    "id": "srvtoolu_1", "name": "web_search", ... },
  { "type": "tool_result", "tool_use_id": "srvtoolu_1", ... },
  { "type": "text", ... } ] }
```

The Messages API rejects that twice: a `tool_result` is only allowed in a
user turn, and a `tool_use` must be answered by a client `tool_result` in
the next user turn. So once the model had used web search, **the next
request in that conversation failed** — the common case of a follow-up
question, with no pause involved.

A `srvtoolu_` call now replays as the `server_tool_use` block it arrived
as, and its result as the matching `web_search_tool_result` /
`web_fetch_tool_result` block with its `content` exactly as the API sent
it — including the `encrypted_content` the API validates on replay. The
result block's type comes from the call's tool name, which is recorded in a
pass over the whole conversation because a paused turn can split a call
and its result across messages.

The set of replayable server tools is upstream's (`web_search`,
`web_fetch`): the ones whose result `content` this client keeps verbatim. A
server tool outside that set is **omitted from the replay together with its
result** — the model loses the record that it called the tool but keeps the
answer it wrote from it, and the request stays valid, where any other
replay of it is a 400.

### A paused turn was returned as finished

A long-running server tool can make the API stop with
`stop_reason: "pause_turn"` before the assistant has finished; the paused
content is meant to be sent back as the trailing assistant turn so the model
continues. `map_stop_reason` folded `pause_turn` into `stop`, so the caller
received the half-finished turn — typically a search call with no answer
after it — as a completed response.

All four clients now continue the turn, as upstream does: up to
`MAX_PAUSE_TURN_CONTINUATIONS` (10, upstream's limit) times, and only while
the paused content can be replayed faithfully
(`convert::is_pause_turn_replayable`: text, signed thinking, and replayable
server tool calls and results). Otherwise the paused response is returned
as it stands rather than resuming from a turn the model did not pause.

- **Non-streaming**: one shared `continue_paused_turns` drives the direct
  API client and the Foundry, Bedrock and Vertex variants — they differ only
  in how a request is sent, which each passes in as a closure — so the four
  cannot drift apart. Each turn's content is merged into one assistant
  message and usage is summed (`convert::merge_pause_turn`); the later
  turn's id, model and finish reason win.
- **Streaming**: the direct client's SSE parser records the raw
  `pause_turn` reason (which `map_stop_reason` still maps to `stop` for the
  caller), and `continue_paused_stream` forwards every update as it arrives,
  rebuilds the paused turn from its updates when the stream ends paused, and
  opens the continuation. The cloud variants already stream by buffering
  `get_response`, so they inherit continuation from it. An error opening a
  continuation is yielded as the stream's last item, not swallowed.

The streaming rebuild is where upstream also had to fix input loss: a
server tool's `input` streams in as `input_json_delta` fragments after an
empty `content_block_start`. Here it shares the client-tool path and is
reassembled correctly — not assumed, tested: the streaming loopback test
splits the query across two fragments and asserts the replayed
`server_tool_use` carries the whole of it.

`crates/agent-framework-anthropic/src/{convert,lib,foundry,bedrock,vertex}.rs`;
unit tests `a_follow_up_after_a_server_web_search_replays_valid_server_blocks`,
`a_web_fetch_result_replays_as_its_own_block_type`,
`a_server_tool_this_client_cannot_replay_is_omitted_with_its_result` and
`a_client_tool_call_still_replays_as_tool_use` (guard); loopback tests in a
new `tests/pause_turn_loopback.rs` against a scripted fake Messages API that
records every request body — `a_paused_turn_is_continued_until_the_model_finishes`,
`the_continuation_replays_the_paused_turn_as_server_tool_blocks`,
`continuation_stops_at_the_limit`,
`a_turn_that_cannot_be_replayed_faithfully_is_returned_paused` (guard) and
`a_paused_stream_is_continued_and_its_streamed_input_survives_replay`.

**Checked and fine:** the function-invocation loop does *not* try to run a
server tool locally. A call answered by a result in the same message is
left alone, which an empirical probe confirmed before any of this was
written — so the defect was confined to replay and to the stop reason.

**Not covered, recorded:** the MCP connector's `mcp_tool_use` /
`mcp_tool_result` blocks have the same replay shape problem, but
`mcp_tool_result` content is parsed recursively rather than kept verbatim,
so it cannot be replayed faithfully without a parser change. Upstream's fix
does not cover it either.

## Already satisfied (checked, nothing to do)

- **#9795 — the shell tool's output limit extended to stderr.** Already true
  here on every path: one-shot processes, persistent sessions and the Docker
  backend all capture stderr in a `HeadTailBuffer` bounded by the same
  `max_output_bytes` as stdout.
- **#9669 — async conditions in switch-case edge groups.** `Condition` is
  already `Fn(&Value) -> BoxFuture<Result<bool>>`, and `Case` holds one;
  async predicates have been supported since the July re-baseline.
- **#9260 — oversized MessagePack history records.** The failure was an
  asymmetry: the writer appended records larger than the reader's 64 MiB
  limit, making the session unreadable. `FileHistoryProvider` here writes
  JSON with no read-side size limit and replaces the file atomically, so the
  asymmetry cannot arise.

## Does not apply

- **#9606 — declarative `InvokeFunctionTool` honouring a registered tool's
  approval requirement.** Lands on declarative workflows, which are out of
  scope (`SCOPE.md`). Worth noting it was a real approval bypass upstream,
  in case declarative workflows are ever reopened.
