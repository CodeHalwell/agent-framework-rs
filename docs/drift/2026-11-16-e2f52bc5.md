## Ported this pass (5 changes, all with regression tests)

### Cached prompt tokens were missing from `input_token_count` on three providers (#9859, #10003)

Anthropic reports `input_tokens` as **only** the tokens after the last cache
breakpoint: `cache_creation_input_tokens` and `cache_read_input_tokens` are
separate figures that it does *not* include. Bedrock Converse does the same
with `inputTokens` against `cacheReadInputTokens` / `cacheWriteInputTokens`.
The framework's `UsageDetails::input_token_count` is the *total* input, as
every other provider reports it and as `gen_ai.usage.input_tokens` is
defined — so on a cached prompt all three of `agent-framework-anthropic`,
`agent-framework-bedrock` and `agent-framework-claude` under-reported the
input by exactly the cached part. With prompt caching doing its job, that is
most of the prompt: a 100-token tail on a 20,000-token cached context
reported 100.

Each converter now folds the cache components back into the total while
keeping them available as their own counts, matching upstream's two fixes.
Bedrock gains the two cache fields outright — it parsed neither before, so
`cache_read_input_token_count` and `cache_creation_input_token_count` were
always `None` there regardless of caching. Its provider-reported
`totalTokens` is still passed through as-is, as upstream does.

The Anthropic streaming path needed one thing beyond a per-snapshot sum.
Anthropic streams *cumulative* usage, and `message_delta` typically repeats
`input_tokens` while omitting the `cache_*` fields that only appeared on
`message_start`. A snapshot that omits them therefore describes a smaller
total than the stream has already seen, and `StreamUsageAccumulator`'s
high-water mark would emit a 0 increment and drop the cached tokens from the
run. The accumulator now carries the last-seen cache components forward and
adds them back, which is what upstream's `raw_usage_carry` does.

`crates/agent-framework-anthropic/src/convert.rs` (new `total_input_tokens`,
`parse_usage`, `parse_message_start_usage`, `StreamUsageAccumulator`),
`crates/agent-framework-bedrock/src/convert.rs` (`parse_usage`),
`crates/agent-framework-claude/src/agent.rs`.

Tests: `parse_usage_input_count_includes_both_cache_components`,
`parse_usage_reports_cache_only_input_when_input_tokens_is_absent`,
`message_start_usage_input_count_includes_cache_components`,
`stream_usage_carries_cache_components_a_later_delta_omits` and
`stream_usage_carry_does_not_double_count_a_repeated_cache_count`
(Anthropic); `parse_usage_input_count_includes_the_cache_components`
(Bedrock); plus the updated expectations in
`parse_response_cache_usage_fields`,
`stream_usage_accumulator_emits_increments_not_cumulative_totals`,
`stream_usage_is_not_double_counted_when_deltas_repeat_input_tokens` and the
Claude `fake_cli` usage assertion, each of which fails pre-fix.
`parse_usage_leaves_input_absent_when_no_component_is_reported`,

### A file skill could run a script the model did not name (#10158)

`Skill::script` resolves a script name **case-insensitively**, and
`Skill::with_script` replaces a same-name script on the same comparison. A
skill package holding both `scripts/Run.py` and `scripts/run.py` — which a
case-sensitive filesystem allows — therefore loaded with only one of them,
whichever `script_files` returned last, and a `run_skill_script` call naming
*either* spelling resolved to that one. The model asks to run one file and a
different file runs, silently. Since `run_skill_script` exists to execute
code, that is the wrong failure mode to leave in.

`FileSkillsSource::load` now detects script names that differ only by ASCII
case — the comparison the lookup itself uses, so the check and the resolver
agree on what "the same name" means — and skips the whole skill with a
warning rather than loading an ambiguous one. That follows upstream, which
rejects such names in the `FileSkill` constructor and skips the affected
skill in its file source.

Resources deliberately get **no** such check: this port looks them up by
exact name (`Skill::resources` is a plain map, and `read_skill_resource`
does an exact `get`), so `README.md` and `readme.md` are two distinct,
individually addressable resources here rather than upstream's ambiguous
pair. The new `case_variant_resource_names_both_load` test pins that
difference so a later change does not quietly import upstream's problem.

`crates/agent-framework-core/src/skills_files.rs` (new
`first_case_variant_pair`); tests
`a_skill_whose_script_names_differ_only_by_case_is_skipped` (fails pre-fix:
the ambiguous skill loads) and `case_variant_resource_names_both_load` (a
guard).

### Purview evaluated a whole batch under one user's identity (#10193, .NET #10099)

Purview evaluates policy *for a user* — the user id is a path segment of the
`processContent` request. `ContentProcessor::evaluate` resolved **one** id
for the whole batch and sent every message under it, so a conversation
carrying more than one participant had each message checked against the
first resolvable participant's policy. In a DLP connector that is both
directions of wrong: one user's content is cleared by another user's
policy, and the audit trail attributes it to someone who did not write it.

Attribution is now per message, mirroring upstream's reworked
`_map_messages`:

- A valid-GUID `provided_user_id` is an **override** and applies to the
  whole batch. That is how a response-phase evaluation reuses the id
  resolved during the prompt phase, and upstream's token-derived identity
  arrives the same way (this port performs no JWT introspection, so it only
  ever arrives as `provided`).
- Otherwise each message is attributed to its own identity — a valid-GUID
  `additional_properties["user_id"]`, else a valid-GUID `author_name` — and
  a message with none inherits the latest explicit identity before it, so an
  assistant or tool message is evaluated under the user it is answering
  without overriding a later participant. Leading messages with no identity
  (a system or generated message) inherit the first explicit one.
- `resolve_user_id` now reports the **last** message's id rather than the
  first, which is what the following response-phase call should be evaluated
  under. Its signature is unchanged.
- No identity anywhere still fails closed, as before.

`crates/agent-framework-purview/src/processor.rs` (new `message_user_id` and
`attributed_user_ids`, rewritten `resolve_user_id`, `evaluate` now zips
messages with their own ids); tests
`each_message_is_attributed_to_its_own_user_id`,
`a_message_without_an_identity_inherits_the_latest_explicit_one`,
`leading_messages_without_an_identity_inherit_the_first_explicit_one`,
`a_provided_user_id_overrides_every_message_identity`,
`resolve_user_id_reports_the_last_messages_id`,
`a_message_user_id_property_beats_its_own_author_name`,
`attribution_is_none_when_no_message_identifies_anyone`, and the end-to-end
`each_message_is_evaluated_under_its_own_user_and_the_response_follows_the_last_speaker`
in `tests/loopback.rs`, which asserts the user id in each captured request
path and fails pre-fix (both prompt requests go to the first user).

### A blocked Gemini prompt reported no finish reason when streaming (#10213)

Gemini answers a blocked prompt with a `200 OK` carrying
`promptFeedback.blockReason`. `parse_response` handled that, but only in its
no-candidates branch, and `parse_stream_chunk` did not handle it **at all** —
so a streaming run whose prompt was refused ended with `finish_reason:
None`, and a caller keying off the finish reason could not tell a content
filter from a normal stop.

Upstream's fix also covers a second shape on both paths: when a later
automatic-continuation hop is blocked, the API keeps the *earlier* candidate
and clears its `finishReason`. That payload has candidates, so this port's
`else if` never looked at `promptFeedback` and the block was lost on the
non-streaming path too.

Both parsers now fall back to `promptFeedback.blockReason` whenever no
finish reason was otherwise determined, through a shared
`prompt_was_blocked`. A candidate that reported a reason of its own keeps
it: the fallback only fills a gap.

`crates/agent-framework-gemini/src/convert.rs`; tests
`parse_response_blocked_prompt_with_a_kept_candidate_sets_content_filter`,
`parse_stream_chunk_blocked_prompt_sets_content_filter` and
`parse_stream_chunk_blocked_prompt_with_a_kept_candidate_sets_content_filter`
(all fail pre-fix), plus the guards
`parse_response_candidate_finish_reason_wins_over_prompt_feedback` and
`parse_stream_chunk_without_a_block_reason_reports_no_finish_reason`.

### The workflow run span now follows the OTel GenAI conventions (#9900, .NET #9899)

Upstream renamed the workflow run span and its name attribute in **both**
languages, flagging it breaking in each. This port was on the old shape: a
span literally named `workflow.run`, a `workflow.name` attribute that was an
empty string for an unnamed workflow, and no `gen_ai.operation.name` — even
though the agent, chat and tool spans here already follow the GenAI
conventions. A backend grouping agent and workflow activity by operation saw
the workflow runs fall outside it.

The run span is now `invoke_workflow {name}` (plain `invoke_workflow` for an
unnamed workflow), carries `gen_ai.operation.name = invoke_workflow`, and
reports its name as `gen_ai.workflow.name`, omitted entirely rather than
sent empty when there is no name. `workflow.id` and `workflow.description`
stay outside the GenAI namespace and the build span stays `workflow.build`,
exactly as upstream keeps them.

This is a **breaking telemetry change**: a dashboard or alert matching
`workflow.run` or `workflow.name` needs updating to `invoke_workflow` and
`gen_ai.workflow.name`.

`crates/agent-framework-core/src/observability.rs` (new
`op::INVOKE_WORKFLOW` and `attr::WORKFLOW_NAME`),
`crates/agent-framework-core/src/workflow/runner.rs`; test
`the_run_span_is_named_after_the_workflow_and_the_genai_operation` in
`tests/workflow_telemetry.rs` (fails pre-fix) and the updated span-name
expectation in `a_run_emits_the_workflow_spans`.

## Azure-ecosystem review

Re-checked every Azure crate this workspace could depend on against the
crates.io API, two weeks after the 2026-11-02 review.
[`docs/azure-rust-sdk.md`](../azure-rust-sdk.md) carries the full table; the
findings are:

**Every stable line is unchanged**, so the pins in `Cargo.toml` are current:
`azure_core` 1.1.0, `azure_identity` 1.0.0, `azure_data_cosmos` 1.0.0,
`azure_storage_blob` 1.1.0, `azure_core_opentelemetry` 1.0.0. Azure AI
Search is still the same `0.0.1` placeholder last published 2025-03-07, and
Foundry, Purview and Copilot Studio still have no official Rust client — the
hand-rolled REST clients in those four crates remain the only option, not a
stopgap.

**One recorded blocker is cleared.** `SCOPE.md` lists the
`azure_core_opentelemetry` bridge — which would carry the Azure SDK's *own*
client spans alongside this crate's — as waiting on that crate moving to
`opentelemetry` 0.32. It has: **1.1.0-beta.2 depends on `opentelemetry` 0.32
and `opentelemetry_sdk` 0.32.1**, matching this workspace exactly. 1.0.0
stable is still on 0.31, so adopting the bridge today means taking a
prerelease Azure dependency, which is not this port's policy. The item
therefore stays open — but it now waits only on **1.1.0 going stable**, not
on upstream deciding to move, and that is what the next pass should check
for rather than re-deriving the version mismatch.

**One standing question is answered.** The Cosmos adoption item asked
whether `azure_data_cosmos` 1.0.0's query surface covers the
`VectorDistance` queries `vector_store.rs` issues. It does:
`ContainerClient::query_items` sends arbitrary Cosmos SQL with parameters,
and `VectorDistance(...)` is evaluated server-side, so it is not a client
feature at all. The `cosmos-sdk` feature sketched in that item can cover
auth, CRUD and the vector queries together, rather than being scoped down
to auth plus plain CRUD as the open question allowed for.

**One item is closed as done.** The review still listed the Blob session
store as needing only an implementation; that store is ported
(`agent-framework-azure`'s `session-store` feature), so the item is now
marked done rather than pending.

No new Azure integration work is required by this window: none of the 198
upstream commits touched an Azure surface this port implements in a way that
changes its shape. The open Azure work is still what `SCOPE.md` records —
the Cosmos DB memory provider (blocked on the Agent Memory Toolkit),
adopting `azure_data_cosmos` behind a feature, and the
`azure_core_opentelemetry` bridge above.
