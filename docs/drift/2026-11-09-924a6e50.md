## Reading the window: a merge-topology trap

A plain `ca65085e..origin/main` on the clone at `/home/user/agent-framework`
reports **310** commits, 155 of them dated 2026-09-09 to 2026-09-30. None of
those are new work, and a pass that triaged them would re-port three
already-closed passes.

The clone is `CodeHalwell/agent-framework`, a fork whose `main` is a chain of
daily `Merge commit '<upstream-sha>'` commits. Upstream's own history is
linear, and every baseline this log has used since `02005995` is a commit on
*that* lineage, not on the fork's merge chain. The fork's `main` therefore
reaches both lineages, including the pre-rewrite September commits that the
post-rewrite linear history no longer carries — so they show up as "not
reachable from the baseline" forever.

The window to diff is along the upstream lineage. `origin/main`'s second
parent is its tip:

```
git log -1 --format='%p' origin/main      # -> <merge-parent> <upstream-tip>
git log --no-merges ca65085e..924a6e50    # 108 commits, 0 merges
```

A sanity check that the range is right: every commit in it is dated inside
the window. September dates in a one-week range mean the merge chain has been
picked up again.

### Notes on three of them

**The citation title was this port's own open question.** `parse_citations`
carried a long comment arguing that upstream's `char_location` branch reading
`citation.title` looked like a copy/paste bug — the Anthropic SDK's
`BetaCitationCharLocation` has no `title`, only `document_title` — but
mirrored it literally anyway, "per this task's mandate to match upstream's
exact behavior". #9898 fixes it upstream the same way, so the comment is now
history and `char_location` reads `document_title`. Every `char_location`
citation had been losing its title in both implementations.

**The schema-ordering one was nearly waved away.** The first reading was
that it could not apply: `serde_json::Map` is a `BTreeMap`, so every schema
is sorted already, and no `Cargo.toml` in the workspace asks for
`serde_json`'s `preserve_order`. Both halves are true and the conclusion was
still wrong. Cargo features unify across a whole build graph, and `bson` —
reached through `agent-framework-mongodb`'s `mongodb` dependency — enables
`serde_json/preserve_order` as a hard dependency feature. So in a workspace
build the map is an insertion-ordered `IndexMap`, and `cargo tree` or a grep
of the *registry sources* (not the workspace manifests) is what shows it.

The practical effect is narrower than upstream's bug: either backing map
gives one binary a stable order, so a provider's prompt cache is not lost
between runs the way Python's was. What it does not give is an order
independent of the dependency set — adding or dropping the MongoDB crate
reorders every tool schema in the process. Canonicalizing closes that and
pins hand-written schemas too, where the caller's literal had decided the
order. Arrays are recursed into but never reordered: `required`, `enum`,
`prefixItems` and the `allOf` / `anyOf` / `oneOf` branches all mean something
in the order given.

**The AG-UI guard is wider here than upstream's.** Upstream's bug was its
last-id cursor: with two declaration-only calls the cursor sat on the second,
so a replay re-started both. This port had no start-once check at all, so it
also emitted a second `TOOL_CALL_START` for any provider that repeats the
function name on each argument fragment. The guard is "is this call still
open", which keeps the legitimate case working: a provider may reuse a call
id for a later, distinct call, and the already-ended occurrence must not
block it. The per-occurrence `started_tools` / `ended_tools` pair this port
already kept is what makes that expressible — upstream needed a third commit
on #9770 to get the same property out of its id-keyed map.

## Does not apply

Grouped, because this window has three families of it.

**The session-based GitHub Copilot agent** (#10088, #9773, #10090, #10149,
#10121). Upstream has two Copilot surfaces: a chat client and a
`GitHubCopilotAgent` built on the Copilot *session* protocol — session
events, `ASSISTANT_USAGE` data, URL-session approvals, file hooks, provider
function middleware. This port implements only the chat client
(`GitHubCopilotChatClient`, the OpenAI-compatible `/chat/completions`
endpoint), so all five land on a surface that does not exist here. This was
not recorded anywhere; `SCOPE.md` now lists it.

**"Prefer an injected client over connection settings"** (#9996, #9991,
#9993, #9987, #9985, #9984, #9983, #9982, #9977, #9969, #9967 — Cosmos,
Foundry embeddings, Qdrant, Azure OpenAI, Oracle, Claude, Postgres, MongoDB,
Redis, Gemini, Bedrock). Upstream's clients take *either* an injected SDK
client *or* environment-derived connection settings through one constructor,
and the bug was settings winning — or still being required — when a client
was passed. This port has no such constructor: `new(...)` takes the
connection explicitly and `from_env()` is a separate entry point, so there is
no precedence to resolve. Two spot-checks of the ones that look closest:
`AzureOpenAIClient::new` takes the deployment as an argument and puts it in
the request path, so no environment alias can shadow it (#9987); and
`FoundryEvals::new` takes the model as a required argument, with no
auto-created client defaulting to `"gpt-4o"` (#9981).

A note for the next pass, since it cost time here: `cargo <cmd> | tail` hides
the exit status behind `tail`'s, so a failing build reports success. Use
`set -o pipefail`, or redirect to a file and check `$?`.
