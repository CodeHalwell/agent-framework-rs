## Ported this pass (6 changes, all with regression tests)

### A change of author mid-stream folded two agents into one message (#9353)

`absorb_update` keyed a streamed update to an existing message by
`message_id`, falling back to the last message of the same role. Two agents
streaming in turn — a sequential orchestration, a handoff — both emit
assistant updates with no `message_id`, telling themselves apart only by
`author_name`. The fallback matched on the role alone, so the second
agent's text was appended to the first agent's message and the later name
overwrote the earlier one: one message, two authors' text, attributed to
whoever spoke last.

The fallback now also requires the authors to be compatible. Only a
*conflict* splits: an update naming no author, or one landing on a message
that has none yet, still continues the message, which is what lets the
first update of a run name the message it started. An explicit
`message_id` still wins over a changed author — the provider said these
fragments are one message, so a renamed author relabels it rather than
splitting it.

`AgentResponse::from_updates` routes through the same function, so the
agent-level aggregation is covered by the one fix.

`crates/agent-framework-core/src/types/response.rs`.

### Exception text was published to telemetry unconditionally (#9288)

`record_error` recorded the error's `Display` text as `otel.status_message`
whatever the configuration. An error's text is not metadata: a provider's
400 quotes the request back, a tool's failure prints the argument it choked
on, a transport error carries the URL — query string, SAS token and all.
Spans leave the process, so this published to the telemetry backend exactly
the content `enable_sensitive_data` exists to withhold, next to the message
content and tool arguments that were correctly gated.

The message is now gated on the same flag. `error.type` and the ERROR
status still always go, so a redacted span still says *that* the call
failed and in which variant — only the free-form text waits for the opt-in.
That is upstream's own split in `capture_exception`.

`record_error` takes the config as a parameter rather than reading a
process-global, which is how this port threads observability settings
everywhere else. The three call sites in `observability.rs` and the one in
the function-invocation loop already had one in scope. `Agent` did not: its
builder consumed the config to wrap the chat client and kept nothing, so
the agent span was the one span with no policy to consult. It now retains
it, defaulting to `ObservabilityConfig::from_env()` — the same rule
`FunctionInvokingChatClient::new` already follows, so one environment flag
governs both rather than the agent span quietly opting itself out.

`crates/agent-framework-core/src/{observability,agent,client}.rs`.

### A fan-out target named twice was delivered to twice (#9432, #9300)

The runner already deduplicated the ids a *selection* returns. Two paths
around it did not:

- **`add_fan_out` / `add_multi_selection`** took the target list verbatim,
  so a broadcast declared with a repeated id ran that executor twice on one
  message — and for a fan-in sink, double-counted toward its barrier. That
  is upstream #9432's second half, the one without a selector.
- **`add_switch`** pushed one target per case, so two cases routing to the
  same executor produced a duplicate edge. Routing survived (the selection
  dedupe caught it at delivery), but the duplicate reached `targets()` and
  `flat_edges()`, so validation and both graph renderings saw an edge that
  does not exist. That is #9300.

Targets are now deduplicated at construction, keeping the order in which
each is first named. For a switch, the branch labels of the cases that
share a target are joined onto the one edge (`"refund, chargeback"`), so
the visualization still names every branch reaching it. The runner's
selector-free branch deduplicates too: `EdgeGroup::FanOut` is a public enum
anyone can build by hand, and a double delivery is silent damage.

`crates/agent-framework-core/src/workflow/runner.rs`.

### Foundry never surfaced an OAuth consent request (#8976)

`Content::OauthConsentRequest` existed in the core content union and had
**no producer anywhere in the workspace**. A Foundry hosted tool that needs
the user to complete an OAuth consent flow finishes its turn with an
`oauth_consent_request` item and no text, so the run came back as an empty
answer with nothing to say what it was waiting for — on the streaming path
as well as the non-streaming one. Upstream had the streaming half already
and added the non-streaming half this window; here neither existed.

Both are handled now, plus the top-level `response.oauth_consent_requested`
event. The item is emitted on `output_item.added` rather than held to
`done` like a hosted MCP call: it has no deltas to wait for, and the run is
blocked on the user until it is answered.

The link is validated before it is handed on — HTTPS with a non-empty host,
the same two things upstream checks. It is a URL the framework is asking a
human to open and authenticate at, arriving from the service as free-form
text, so an `http://` or `javascript:` one is dropped with a warning rather
than surfaced as something to click.

`OauthConsentRequestContent` gained an `id`: a consent request is a
user-input request, and a workflow registers it under the provider's item
id to match the user's answer back to it.

This lands in `agent-framework-openai`'s Responses parser rather than the
Foundry crate, because `FoundryChatClient` delegates request and response
conversion wholesale to `agent_framework_azure::responses`, which reuses
that parser — the architecture the crate docs describe. OpenAI never emits
the item, so the cost is one unreachable match arm on that path.

`crates/agent-framework-openai/src/responses.rs`,
`crates/agent-framework-core/src/types/content.rs`.

### The hosting Responses route dropped image and file input (review-surfaced, cites #9298)

Triaging upstream's narrow fix — a data URL's declared media type being
overwritten with `image/*` — found a wider hole on this side.
`content_text` kept only the content parts carrying a `text` field, so an
`input_image` or `input_file` part was discarded and the hosted agent was
asked about an attachment it had never been given. The client half of this
stack has carried multimodal input for some time; the hosting half silently
did not.

Content parts are now converted individually: `input_text` / `output_text`
/ `text` to text, `refusal` to a marked refusal (a replayed assistant turn
can carry one, and it must not read as the answer), `input_image` and
`input_file` to data or URI content. A `data:` URL keeps the media type it
declares, which is upstream's #9298 — `image/*` is not enough for a
converter, since Anthropic and Gemini both need the concrete type to accept
the attachment. A remote URL declares nothing, so it keeps the generic
type. A part with no URL at all is skipped rather than failing the request,
and the rest of the message survives.

`crates/agent-framework-hosting/src/responses.rs`.

### One unknown name in a Magentic ledger ended the whole run (#9181)

`create_progress_ledger` retried a ledger that would not parse, up to
`progress_ledger_retry_count`. A ledger that parsed but named a participant
that does not exist got no retry: the orchestrator found no such agent and
ended the run with a prepared final answer. A ledger naming a ghost is as
unusable as one that will not parse, and the budget already existed for
exactly that.

The unknown name now spends the same budget. The last such ledger is kept,
so if every attempt names one, returning it hands the orchestrator the
invalid-speaker case it already handles — an error there would instead read
as a parse failure and trigger a reset-and-replan. A satisfied request is
returned whatever it names: the final answer is about to be prepared and
the speaker is never consulted.

`crates/agent-framework-core/src/workflow/orchestration/magentic.rs`.

## Second pass: AG-UI thread snapshots (0.13.0)

The first pass found the window's eight AG-UI hardening commits — #9413,
#9316, #9368, #9367, #9365, #8851, #8273, #8714 — inapplicable because the
router persisted nothing, and recorded the missing store as a gap. This
pass builds the store, so those commits now apply, and their lessons are
the design:

- **#9413, #9316 — explicit authorization scope.** Snapshots are keyed by
  scope and thread id; a store without an authorization mode does not
  build. `AgUiRouter::authorization_scope` resolves the scope from the
  request head before the body is read; `single_user` declares one
  principal with an opaque per-route scope.
- **#9368 — client state is not server state.** Client shared state is
  merged into the thread's session minus anything shaped like
  tool-approval state, and minus any key the server wrote. **Tightened
  beyond upstream:** upstream checks three `ToolApprovalState` fields; this
  checks all five. `held_messages` is replayed into the inner run as input
  and `pending_standing_approvals` turns a one-off approval into a rule, so
  the two upstream misses let a client plant an approval response on a
  fresh thread and run a tool unprompted. A test pins the list to the
  struct.
- **#9365 — interrupts are bound to their thread.** A resume must answer
  exactly the interrupts stored for that scope and thread; the approved
  call is rebuilt from the stored record.
- **#8851, #8273, #8714, #9367** — queued approval results, workflow HITL
  text, custom approval namespaces and FIDES session state are all shapes
  of upstream's snapshot bookkeeping that this store's simpler model
  either covers (approvals ride the interrupt list; the transcript records
  user turns) or has no counterpart for (no FIDES, no workflow runner on
  this route).

The transcript reconciliation is a port of upstream's
`_reconstruct_messages_from_thread_snapshot` and `_filter_untrusted_suffix`.

### What the review of the store caught

An adversarial review of the first implementation, before it shipped,
confirmed two bugs and four smaller faults. All are fixed, each with a
regression test that fails against the reviewed code:

- **Critical — client state could run a tool unprompted.** The shape
  check covered upstream's three fields; `held_messages` carried an
  approval response straight into the function-invocation loop. Fixed as
  above.
- **High — an approved call could run twice.** The interrupt was cleared
  only by the final save, so a run that failed after the tool executed — or
  two concurrent resumes — left it resumable. Interrupts are now spent
  before the agent runs (at most once; if the store cannot record that,
  nothing runs), and turns on one thread are serialized in-process.
- **A resumed run emitted `TOOL_CALL_END` with no matching start.** Ends
  are now emitted only for calls the run started — in stateless mode too.
- **History reconciliation was id-only and trusted every role**, so an
  id-less replay doubled the transcript and a client could store forged
  `system` or `assistant` turns. Replaced by the upstream port.
- **The stored transcript collapsed a run's text after its tool work**, and
  an unanswered frontend tool call broke every later turn on the thread
  (an unanswered call is a provider 400). Output is now recorded in order,
  and unanswered calls are kept in the record but not sent.
- **Smaller:** an empty `threadId` returned 500 (now 400); a resume entry
  naming the interrupt by `toolCallId` was not found; the Magentic
  unknown-speaker message carried a run of stray spaces; hosting
  `input_file` ignored `file_id` and bare-base64 `file_data`, and a
  malformed `data:` URL became an unfetchable URI.

Codex's review of the PR then found two more, both fixed with regression
tests that fail against the reviewed head:

- **Client keys could claim server-owned session state.** Ownership was
  read off the stored shared state, which keeps every key the client sent,
  refused ones included. A client could send a key on the turn that
  pauses, let the server write its own value there, and overwrite it on
  the next turn. Worse, the function-invocation loop reads
  `__af_function_invocation_budget__` at the start of every run, so seeding
  it on a fresh thread reset `max_function_calls` and
  `max_duration_seconds` outright. The snapshot now tracks client-owned
  keys itself, ownership follows the server's writes, and the `__af_` and
  `__ag_ui` prefixes are reserved.
- **A reused call id dropped a completed declaration.** The paused call
  was filtered out of the transcript by id, taking an earlier completed
  call with the same id with it and orphaning its result. Only the latest
  declaration is now left out.

Its re-review of the fix found three more, also fixed with failing-first
tests: `TOOL_CALL_END` tracked per id rather than per occurrence (a reused
id's second call got no end); unanswered-call pruning paired results by id
rather than in order (an earlier result vouched for a later reused-id
call); and a turn sent while approvals were pending saved over them. That
last now fails with `APPROVAL_RESUME_REQUIRED`, upstream's contract.

A third Codex round found the same reused-id pairing fault in snapshot
reconciliation (a later call's legitimate result was refused), an
`input_image` given by `file_id` reaching the provider as an `input_file`
(now skipped, as upstream rejects it), and the OpenAI Responses converter
sending remote file URLs under `file_data` (now `file_url`). All fixed with
failing-first tests.

A fourth round found that stored approvals dropped the call's occurrence
id (two pending approvals under one reused `call_id` could then resolve each
other on resume) — fixed by persisting it, along with the call's provider
replay token (Gemini's signature), which had the same gap — and that a
duplicated tool result was admitted twice, orphaning the second. Admission
now spends one open call per accepted result.

A fifth round found that a stored approval dropped arguments that did not
parse, so approving a malformed call ran it with an empty argument map
instead of refusing it (the raw string is now kept), and that hydration
read without the thread lock and could observe a resume between spending
its interrupts and saving its outcome (it now takes the lock).

A sixth round found the OAuth consent-link check accepting links with an
authority but no host (`https://user@/consent`) — it now also parses the
link and requires a real host — and the OpenAI Responses converter dropping
`text/*` files, which it now sends as `input_file`.

A seventh round found the `toolCallId` resume alias resolving every
entry to one interrupt when two pending approvals shared a reused id (each
entry now takes a distinct one), and pending approvals admitting a
client-supplied result for their call — output for a call nobody had
allowed, stored with no declaration before it. **Divergence:** upstream
admits these, because its transcript keeps the declaration; this one does
not, so they are refused.

An eighth round found the snapshot transcript dropping a tool call's
provider replay token, so a completed Gemini call replayed on the next turn
without its `thoughtSignature` and was rejected; it now rides as the call's
`encryptedValue`. It also found that an agent with a default
`ChatOptions::conversation_id` falls back to it on a snapshot run, getting
each turn twice — documented as unsupported here, since clearing a default
needs a new core run option, and such an agent would share one service
conversation across every caller on any hosting route anyway.

A ninth round found Gemini's fallback signature placement — on the thought
part just before a call, which itself carries none — unrecorded, so such a
call replayed unsigned. The framing now pairs a signed reasoning part with
the call that immediately follows it, by the Gemini converter's own rule:
the call's own token wins, and visible content in between breaks the pair.

A twelfth round found that a failed final save still sent
`MESSAGES_SNAPSHOT` and `RUN_FINISHED`, advertising approval interrupts that
were never stored — and, after a resume whose approval was already spent, an
outcome the thread does not record. **Divergence:** upstream logs and
finishes; here the run ends with `RUN_ERROR` (`SNAPSHOT_SAVE_FAILED`) in
place of those closing events.

A thirteenth round found that a trusted suffix message was stored exactly
as sent: the message mapper reads `toolCalls` whatever the role, so a
"user" turn carrying them planted an assistant call in the server's record,
which the next turn could answer with a forged result. Admitted messages are
now rebuilt from only the fields their role may carry.

A fourteenth round found that a frontend call the user moved on from stayed
answerable, so a late result was admitted after intervening turns, which
Anthropic rejects. A call is now open only while nothing but tool results
follows it.
